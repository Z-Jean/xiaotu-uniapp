# 小兔鲜儿 — 答辩演讲稿

> 答辩时间：约 15-20 分钟
> 配合 PPT 使用，逐页讲解

---

## 开场（1 分钟）

各位老师好，我是 XXX，我的毕业设计项目是**小兔鲜儿**，一个基于 uni-app 的鲜食电商平台。

这个项目的核心特点是**一套代码三端运行**——同时支持 H5 网页、微信小程序和 App 三个平台。项目包含了完整的电商功能，从商品浏览到下单支付，还集成了 AI 智能购物助手。

下面我从技术架构、核心亮点、技术难点三个方面进行汇报。

---

## 第一部分：技术架构（2 分钟）

### 项目定位

小兔鲜儿是一个鲜食电商平台，主要销售水果、蔬菜、肉蛋等生鲜食品。

### 技术栈

- **前端**：uni-app + Vue3 + TypeScript + Pinia
- **后端**：Express.js + TypeScript + MySQL
- **外部服务**：阿里云 OSS、高德地图、MiMo AI、阿里云短信
- **部署**：Docker + Docker Compose + GitHub Actions

### 架构设计

整体架构分为三层：

1. **前端层**：使用 uni-app 跨平台框架，通过条件编译适配三端
2. **后端层**：Express.js 提供 RESTful API，集成了 JWT 认证、OSS 上传、AI 聊天等功能
3. **数据层**：MySQL 存储用户、商品、订单等业务数据

## 第二部分：核心技术亮点（8 分钟）

### 亮点 1：多端条件编译

**问题**：H5 用 `localhost`，小程序不允许；微信有 `wx.chooseMedia`，H5 没有。

**解决方案**：uni-app 的条件编译技术，通过 `#ifdef` / `#ifndef` 指令，在编译时隔离不同平台的代码。

**项目实践**：在 14 个文件中使用了 37 处条件编译，覆盖 H5、微信小程序、App 三端。

**举例**：同一个"图片转 Base64"功能，三个平台使用完全不同的原生 API：
- H5 用浏览器的 FileReader
- 微信小程序用 FileSystemManager
- App 端用 5+ API 的 plus.io.FileReader

这些代码共存于同一个文件，编译时自动隔离。

### 亮点 2：SKU 商品规格管理

**问题**：一个手机有 6 种颜色和 3 种容量，会产生 18 种组合，每种都有独立的价格和库存。

**解决方案**：设计了 SPU-SKU-Specs 三层数据结构，通过路径检查算法实现规格联动选择。

**算法原理**：
1. 将所有 SKU 的规格组合存入 `shopItemInfo` 字典
2. 用户每次选择时，遍历其他维度的可选值
3. 检查当前已选的规格加上用户点击的值是否存在于字典中
4. 存在则可选，不存在则灰显
5. 所有维度都选完时，取出对应的 SKU 显示价格和库存

### 亮点 3：AI 智能购物助手

**技术选型**：LangChain + 小米 MiMo LLM

**架构设计**：
1. **确定性意图识别**：用 17 个关键词映射到商品分类，避免依赖 LLM（成本高、延迟大）
2. **LangChain Tool 调度**：定义搜索、分类、推荐三个工具，由 LLM 根据用户意图自动调用
3. **自定义 LLM 适配器**：继承 LangChain 的 BaseChatModel，对接 MiMo API
4. **SSE 流式输出**：H5 端实现逐字显示，小程序端降级为普通请求

**降级策略**：API 异常时自动返回商品推荐列表，不影响用户体验。

### 亮点 4：Docker 容器化部署

**问题**：传统部署需要手动安装 Node.js、MySQL、Nginx，环境不一致会导致"在我电脑上能跑"的问题。

**解决方案**：Docker Compose 编排三个容器：
- Nginx：前端静态文件 + API 反向代理
- Backend：Express.js 业务逻辑
- MySQL：数据存储 + Volume 持久化

**多阶段构建**：前端 Dockerfile 采用两阶段构建，构建阶段用 node:20-alpine 编译代码，运行阶段用 nginx:alpine 只复制静态文件。最终镜像从 200MB 减小到 50MB，减少了 75%。

**自动部署**：通过 GitHub Actions 实现 push-to-deploy，开发者只需 git push，服务器自动更新。

### 亮点 5：阿里云 OSS

**关键设计**：Multer 内存存储 + ali-oss SDK 直传

文件在服务端不落盘，直接从内存传到 OSS，减少了服务器 IO 压力。AccessKey 通过环境变量管理，不硬编码在代码中。

图片代理设置了域名白名单，只允许访问指定的 OSS 域名，防止 SSRF 攻击。

## 第三部分：技术难点（3 分钟）

### 难点 1：跨平台兼容

**问题**：三端 API 差异大，同一功能需要不同实现。

**解决方案**：条件编译 + 适配器模式。通过 `#ifdef` 指令在编译时隔离平台代码，通过适配器封装统一接口。

### 难点 2：SKU 规格联动

**问题**：规格组合数量爆炸，需要实时计算可选状态。

**解决方案**：路径检查算法，维护 `shopItemInfo` 字典存储所有组合，用户选择时遍历检查。

### 难点 3：AI 集成

**问题**：需要 Tool 编排能力，但不想依赖 OpenAI。

**解决方案**：LangChain Tools + 自定义 LLM 适配器。利用 LangChain 的 Tool 调度框架，自定义 MiMoChatModel 对接小米 MiMo API。

### 难点 4：小程序状态持久化

**问题**：Pinia 默认持久化只支持 localStorage，仅在 H5 端生效。

**解决方案**：自定义 storage 接口，使用 `uni.setStorageSync` 封装，这个 API 在三端都可用。

## 答辩问题准备

### Q1：为什么选择 uni-app 而不是原生开发？

**回答**：uni-app 一套代码可编译到 H5、微信小程序、App 三端，维护成本低。条件编译技术可以处理平台差异，实现 90%+ 代码复用。如果用原生开发，需要维护三套代码，工作量是三倍。

### Q2：SKU 选择的核心算法是什么？

**回答**：路径检查算法。我们将所有 SKU 的规格组合存入 `shopItemInfo` 字典，key 是规格值的组合（如"红色,256G"），value 是对应的 SKU 对象。用户每次选择时，我们遍历其他维度的可选值，检查当前已选的规格加上用户点击的值是否存在于字典中。存在则可选，不存在则灰显。当所有维度都选完时，取出对应的 SKU 显示价格和库存。

### Q3：为什么用 LangChain 而不是直接调用 AI API？

**回答**：LangChain 提供了 Tool 编排框架，可以定义多个工具（搜索、分类、推荐），由 LLM 根据用户意图自动调用。如果直接调用 API，需要自己实现 Tool 调度逻辑。LangChain 还提供了 Memory、Chain 等抽象，方便管理对话历史和流程编排。

### Q4：Docker 多阶段构建的好处是什么？

**回答**：构建阶段使用完整的 Node.js 环境编译代码，运行阶段仅包含 Nginx + 静态文件。最终镜像从 200MB 减小到 50MB，减少了 75%。同时不含构建工具和源码，减少了攻击面，提升了安全性。

### Q5：如何保证 API 安全？

**回答**：三层防护：
1. JWT 认证：7 天有效期，中间件统一校验，401 自动跳转登录
2. SSRF 防护：图片代理设置域名白名单，只允许访问指定的 OSS 域名
3. 配置外置：所有敏感配置（数据库密码、API Key）通过环境变量管理，不入代码仓库

### Q6：短信验证码如何防止恶意刷取？

**回答**：三重防护：
1. 前端：60 秒倒计时，防止频繁点击
2. 后端：10 秒频率限制，同手机号短时间内不能重复发送
3. 阿里云平台级频率控制，防止接口被滥用

验证码还有 5 分钟有效期和一次性使用的限制。

### Q7：地图功能如何实现三端适配？

**回答**：我们设计了三端适配方案：
- H5 端：使用高德 JS API v2.0，绘制贝塞尔曲线轨迹
- App 端：使用高德静态地图图片，图片内绘制 polyline 和 markers
- 小程序端：使用原生 `<map>` 组件，通过 polyline 和 markers 属性绘制

通过条件编译在各端渲染不同的地图实现，保证各端的最佳体验。

### Q8：Pinia 持久化如何兼容小程序？

**回答**：自定义 storage 接口，使用 `uni.setStorageSync` / `uni.getStorageSync` 封装。这两个 API 是 uni-app 提供的跨平台 API，在 H5、小程序、App 三端都可用。H5 端底层是 localStorage，小程序端底层是小程序本地存储，App 端底层是 native 存储。
