## 一、项目概述

### 1.1 项目业务背景、开发目标、适用场景、用户群体

#### 业务背景

**小兔鲜儿**是一款面向 **鲜食 / 品质生活消费** 场景的移动端电商平台，覆盖居家日用、服饰、母婴、美食、数码、运动等品类。项目从「浏览商品 → 选规格加购 → 下单支付 → 物流跟踪 → 售后管理」完整打通电商主链路，并叠加 **AI 智能导购**、**地图物流可视化** 等差异化能力。

行业痛点：传统生鲜/品质电商用户决策成本高（品类多、规格复杂）、小程序端转化链路长、跨端维护成本高。本项目以 **一套代码三端发布** 降低研发成本，以 **SKU 精细化库存模型** 和 **AI 对话式导购** 提升转化效率。

#### 开发目标

| 目标维度 | 具体目标 |
|---------|---------|
| 业务闭环 | 完成首页、分类、购物车、订单、支付、地址、个人中心等核心电商流程 |
| 技术能力 | 掌握 uni-app 跨端、Vue3 组合式 API、TypeScript 类型体系、Pinia 状态管理 |
| 全栈能力 | 自研 Express + MySQL 后端，替代纯 Mock，实现真实数据持久化 |
| 工程化 | Docker 容器化 + Nginx 反代 + GitHub Actions CI/CD 一键部署 |
| 智能化 | 集成 LangChain + 小米 MiMo LLM，实现对话导购、图片分析、商品推荐 |
| 合规安全 | JWT 鉴权、短信验证码登录、隐私协议校验、SSRF 防护 |

#### 适用场景

- **微信小程序**：主战场，利用微信生态流量与 `open-type` 原生能力（客服、授权登录）
- **H5**：浏览器调试、分享传播、AI SSE 流式对话最佳体验端
- **App（uni-app 编译）**：可扩展为独立 App，复用同一套业务代码

#### 用户群体

- **C 端消费者**：18–45 岁，注重生活品质，习惯移动端购物，偏好「少操作、快决策」
- **运营/答辩受众**：需要看到完整电商能力 + 技术亮点（跨端、AI、容器化）的项目展示

### 1.2 整体架构选型理由

#### 前端：uni-app + Vue3 + TypeScript

| 选型 | 理由 | 放弃的同类方案 |
|------|------|---------------|
| **uni-app** | 一套代码编译 H5 / 微信 / App；`#ifdef` 条件编译处理平台差异；生态成熟（uni-ui、插件市场） | **原生微信 + 原生 App**：双团队维护，成本翻倍；**Taro**：React 栈，团队 Vue 背景不匹配；**Flutter**：学习曲线陡，小程序支持弱 |
| **Vue3 Composition API** | 逻辑复用（`composables`）、更好的 TS 推导、性能优于 Options API | **Vue2**：已停止主流更新；**React**：团队技术栈统一为 Vue |
| **TypeScript** | 接口响应、SKU 结构、订单状态在编译期校验，减少线上类型错误 | **纯 JavaScript**：大型项目维护困难 |
| **Pinia** | 轻量、TS 友好、模块化；配合 `pinia-plugin-persistedstate` 做登录态持久化 | **Vuex**：模板代码多，TS 支持弱 |
| **Vite** | 通过 `@dcloudio/vite-plugin-uni` 实现秒级 HMR | **Webpack**：冷启动慢 |

#### 后端：Express.js + TypeScript + Sequelize

| 选型 | 理由 | 放弃方案 |
|------|------|---------|
| **Express** | 轻量、路由清晰、中间件生态丰富，适合 RESTful API 快速搭建 | **NestJS**：对本项目体量偏重；**Koa**：中间件洋葱模型学习成本略高 |
| **Sequelize ORM** | 模型与 MySQL 表映射清晰，支持 `include` 关联查询（购物车 JOIN SKU JOIN 商品） | **原生 SQL**：开发效率低；**Prisma**：团队更熟悉 Sequelize |
| **JWT** | 无状态鉴权，适合前后端分离 + 多端共用同一 API | **Session**：跨域、小程序端 Cookie 管理麻烦 |

#### 数据与基础设施

| 技术 | 理由 |
|------|------|
| **MySQL 8.0** | 电商事务、关系型数据（订单-订单项-用户）天然契合；JSON 字段存规格、地址快照 |
| **阿里云 OSS** | 图片海量存储、CDN 加速、服务端不落盘直传 |
| **Docker Compose** | Nginx + Backend + MySQL 三容器编排，环境一致、一键部署 |
| **LangChain + MiMo** | Tool 编排商品查询；国产 LLM 降低 API 成本与合规风险 |

### 2.1 前端技术

#### uni-app

- **基础定义**：基于 Vue 的跨端应用框架，通过编译器将 `.vue` 源码分别编译为各平台原生或 Web 代码。
- **核心原理**：运行时差异通过 **条件编译**（`#ifdef MP-WEIXIN`）在构建期剪枝；API 统一为 `uni.*` 封装各平台原生能力。
- **本项目落地**：
  - 主包 8 页面 + 2 分包（`pagesMember`、`pagesOrder`），TabBar 四入口
  - `pages.json` 配置 `easycom` 自动引入 `uni-*` 与 `Xtx*` 组件
  - `src/config/index.ts` 按 H5 / 非 H5 配置不同 `API_BASE`
  - 全项目约 **16 个文件、37+ 处** 条件编译（API 地址、图片 Base64、地图、AI 流式等）
- **选型优势**：代码复用率 90%+，答辩可量化「一套代码三端」。

#### Vue 3 Composition API

- **基础定义**：用 `setup` + `ref`/`reactive` + 组合式函数组织逻辑，替代 Options API 的 data/methods 分散写法。
- **核心原理**：逻辑按功能聚合，通过 `composables` 跨页面复用（如 `useGuessList` 猜你喜欢触底加载）。
- **本项目落地**：全部页面 `<script setup lang="ts">`；`src/composables/index.ts` 封装猜你喜欢逻辑。
- **选型优势**：首页并行请求、下拉刷新与触底加载逻辑清晰可测。

#### TypeScript

- **基础定义**：JavaScript 的超集，增加静态类型检查。
- **核心原理**：编译期发现类型错误；泛型实现 API 响应类型自动推导。
- **本项目落地**：
  - `src/types/` 按业务拆分：`goods.d.ts`、`order.d.ts`、`cart.d.ts` 等
  - `http<T>()` 泛型封装，`await http<GoodsResult>(...)` 自动推断 `result` 类型
  - `PageResult<T>` 通用分页类型复用
- **选型优势**：商品 SKU、订单状态枚举在 IDE 内自动补全，减少接口字段拼写错误。

#### Pinia + pinia-plugin-persistedstate

- **基础定义**：Vue 官方推荐的状态管理库；持久化插件将 Store 同步到本地存储。
- **核心原理**：每个 Store 独立模块；持久化通过自定义 `storage` 适配不同平台 API。
- **本项目落地**：`useMemberStore` 持久化 `profile`（含 token）；自定义 `uni.getStorageSync` / `setStorageSync` 适配三端。
- **选型优势**：解决默认插件仅支持 `localStorage`（H5）导致小程序登录态丢失的问题——典型 **适配器模式** 答辩点。

#### uni-ui + easycom

- **基础定义**：DCloud 官方 UI 组件库；easycom 按命名规则自动注册组件，无需手动 import。
- **核心原理**：`pages.json` 中 `^uni-(.*)` 正则匹配组件路径，构建时自动解析。
- **本项目落地**：`uni-icons`、`uni-data-picker`（H5 地址选择）、`uni-load-more` 等直接使用。
- **选型优势**：减少样板代码，组件按需打包。

#### SCSS

- **基础定义**：CSS 预处理器，支持变量、嵌套、混入。
- **核心原理**：编译为普通 CSS；`uni.scss` 注入全局变量。
- **本项目落地**：`src/styles/base.scss`、`uni.scss` 主题色 `#27ba9b`；页面级 `styles/*.scss` 拆分。
- **选型优势**：多端样式统一管理，主题色一处修改全局生效。

#### Vite + @dcloudio/vite-plugin-uni

- **基础定义**：下一代前端构建工具，开发时利用浏览器原生 ESM 实现快速热更新。
- **核心原理**：开发服务器按需编译模块；生产构建 Rollup 打包。
- **本项目落地**：`pnpm dev:h5` → `localhost:5173`；`pnpm dev:mp-weixin` → `dist/dev/mp-weixin`。
- **选型优势**：H5 调试体验接近原生 Vue 项目。

### 2.2 后端技术

#### Express.js

- **基础定义**：Node.js 极简 Web 框架，通过中间件处理 HTTP 请求。
- **核心原理**：请求 → 中间件链（cors、json 解析、auth）→ 路由处理器 → 响应。
- **本项目落地**：`server/app.ts` 挂载 15+ 路由模块；统一 `{ code, msg, result }` 响应格式。
- **选型优势**：路由按业务拆分（`home.ts`、`goods.ts`、`ai.ts`），结构清晰适合答辩讲解分层。

#### Sequelize ORM

- **基础定义**：Node.js 对象关系映射库，用 Model 描述数据库表。
- **核心原理**：Model 实例 ↔ SQL 自动转换；`findAll` + `include` 实现 JOIN。
- **本项目落地**：
  - `server/models/` 定义 User、Goods、GoodsSku、Order、CartItem 等
  - 购物车查询：`CartItem.findAll({ include: [{ model: GoodsSku, include: [Goods] }] })`
- **选型优势**：避免手写大量 JOIN SQL，模型即文档。

#### JWT（jsonwebtoken）

- **基础定义**：JSON Web Token，无状态身份凭证，由 Header.Payload.Signature 三部分组成。
- **核心原理**：服务端用密钥签名；客户端每次请求携带 `Authorization` 头；服务端 `verify` 解析 `userId`。
- **本项目落地**：
  - 登录成功 `jwt.sign({ userId }, secret, { expiresIn })`
  - `server/middleware/auth.ts` 拦截需登录接口
  - 前端 `http.ts` 拦截器自动注入 token，401 清 profile 并跳转登录
- **选型优势**：多端共用同一套鉴权，无需 Session 粘滞。

#### bcryptjs

- **基础定义**：密码单向哈希库，防止明文存储。
- **核心原理**：加盐哈希，验证时 `compare` 而非解密。
- **本项目落地**：账号密码登录、微信模拟注册时 `bcrypt.hash('123456', 10)`。
- **选型优势**：符合安全基线。

#### Multer

- **基础定义**：Express 文件上传中间件。
- **核心原理**：`memoryStorage` 将文件读入内存 Buffer，不落磁盘。
- **本项目落地**：`server/routes/upload.ts` 头像上传 → Buffer 直传 OSS。
- **选型优势**：减少服务器 IO，适合容器 ephemeral 文件系统。

#### Zod + LangChain DynamicStructuredTool

- **基础定义**：Zod 是 TS 优先的 schema 校验库；LangChain Tool 让 LLM 可调用外部函数。
- **核心原理**：用 Zod 定义 Tool 入参结构；`func` 内执行数据库查询返回 JSON 字符串。
- **本项目落地**：`search_goods`、`category_goods`、`recommend_goods` 三个 Tool。
- **选型优势**：Tool 入参类型安全，LLM 调度有结构化约束。

### 2.3 数据库

#### MySQL 8.0

- **基础定义**：开源关系型数据库，支持 ACID 事务。
- **核心原理**：InnoDB 引擎行级锁；JSON 类型字段存储半结构化数据（规格、图片数组）。
- **本项目落地**：14 张核心业务表；Docker Volume `mysql_data` 持久化。
- **选型优势**：订单、购物车、用户关系清晰；答辩可讲 ER 与索引设计。

---

### 2.4 中间件 & 云服务

#### Nginx

- **基础定义**：高性能 Web 服务器与反向代理。
- **核心原理**：`proxy_pass` 将 API 请求转发到后端容器；`try_files` 支持 SPA 路由。
- **本项目落地**：`nginx/default.conf` 静态资源 30 天缓存 + Gzip + 安全响应头；按路径代理 `/home/`、`/ai/` 等。
- **选型优势**：前后端同域部署，H5 生产环境 `API_BASE` 可为空字符串，避免跨域。

#### 阿里云 OSS

- **基础定义**：对象存储服务，按 Bucket/Key 存取文件。
- **核心原理**：HTTP API 上传；返回公网 URL；可配 CDN。
- **本项目落地**：用户头像 `avatars/avatar_{timestamp}_{random}.ext`；环境变量注入 AccessKey。
- **选型优势**：图片与业务服务器解耦，扩容无需加磁盘。

#### 阿里云短信（号码认证服务 API）

- **基础定义**：通过 API 向手机号发送验证码短信。
- **核心原理**：`SendSmsVerifyCode` 接口 + 模板参数 `{ code, min }`。
- **本项目落地**：`server/routes/sms.ts`；验证码存 `sms_codes` 表，5 分钟有效、一次性使用。
- **选型优势**：无密码登录，符合小程序用户习惯。

#### 高德地图 Web API

- **基础定义**：地理编码、路线规划等 LBS 能力。
- **核心原理**：地址文字 → `geocode` → 经纬度；两点 → `direction/driving` → polyline 轨迹。
- **本项目落地**：`server/routes/map.ts` 后端代理（保护 Key）；前端 `LogisticsMap.vue` 三端差异化渲染。
- **选型优势**：Key 不暴露在前端包内（经后端转发）。

### 2.5 部署 & CI/CD

#### Docker

- **基础定义**：容器化技术，将应用与依赖打包为镜像，与环境无关地运行。
- **核心原理**：镜像分层只读；容器可写层隔离；Compose 多服务编排。
- **本项目落地**：
  - 前端 **多阶段构建**：Node 构建 H5 → 仅 Nginx + 静态文件（约 50MB）
  - 后端 **多阶段构建**：编译 TS → 生产依赖 + 非 root 用户 `appuser`
  - `docker-compose.yml`：nginx:80、backend:3000、mysql:3306
- **选型优势**：「在我电脑能跑」问题消失；答辩可演示 `docker compose up -d`。

#### GitHub Actions

- **基础定义**：GitHub 内置 CI/CD，push 触发自动化流程。
- **核心原理**：`on: push: branches: [main]` → SSH 登录服务器 → `git pull` + `docker compose up -d --build`。
- **本项目落地**：`.github/workflows/deploy.yml` + Secrets（HOST、USER、SSH_KEY）。
- **选型优势**：Push-to-Deploy，体现 DevOps 能力。

### 2.6 AI 集成

#### LangChain

- **基础定义**：LLM 应用开发框架，提供 Chain、Tool、Memory 等抽象。
- **核心原理**：将外部能力封装为 Tool，由模型或编排逻辑调用。
- **本项目落地**：自定义 `MiMoChatModel extends BaseChatModel`；三个 `DynamicStructuredTool` 查库；**意图识别用关键词映射表而非 LLM**（降本降延迟）。
- **选型优势**：Tool 层可复用，换模型只需改 ChatModel 适配器。

#### 小米 MiMo LLM（mimo-v2.5）

- **基础定义**：国产大语言模型 API，兼容 OpenAI Chat Completions 格式。
- **核心原理**：POST `/v1/chat/completions`；支持 `stream: true` 流式输出；支持多模态 `image_url`。
- **本项目落地**：对话、SSE 流式、图片分析三条链路；API Key 环境变量 `MIMO_API_KEY`。
- **选型优势**：国内访问稳定；答辩可对比 OpenAI 方案说明国产化选型。

#### SSE（Server-Sent Events）

- **基础定义**：服务端单向推送事件流，基于 HTTP 长连接。
- **核心原理**：`Content-Type: text/event-stream`；每行 `data: {...}\n\n`；客户端 `fetch` + `ReadableStream` 逐块读取。
- **本项目落地**：`/ai/chat/stream` 先推 `goods` 事件再推 `chunk` 文字；H5 端 `ChatPanel` 实时打字效果。
- **选型优势**：比 WebSocket 简单，适合单向 AI 输出；小程序端降级为普通 POST（平台限制）。

**各层职责一句话**：

| 层级 | 职责 |
|------|------|
| 表现层 | 用户交互、组件复用、多端 UI 差异 |
| 客户端服务层 | API 封装、状态管理、请求拦截 |

#### 表结构总览（14 张核心表）

| 表名 | 说明 | 主键 |
|------|------|------|
| `users` | 用户账号 | `id` AUTO_INCREMENT |
| `sms_codes` | 短信验证码 | `id` |
| `categories` | 首页一级分类 | `id` |
| `goods_categories` | 商品二级分类 | `id` |
| `goods` | 商品 SPU | `id` |
| `goods_specs` | 规格维度定义 | `id` |
| `goods_skus` | 库存单元 SKU | `id` |
| `banners` | 首页轮播 | `id` |
| `hot_items` | 热门推荐 | `id` |
| `cart_items` | 购物车 | `id` |
| `addresses` | 收货地址 | `id` |
| `orders` | 订单主表 | `id` |
| `order_skus` | 订单商品明细 | `id` |

#### SPU-SKU-Spec 三层模型（电商核心）

```
goods (SPU)                 goods_specs              goods_skus (SKU)
┌─────────────┐            ┌──────────────┐         ┌─────────────────┐
│ id          │◀───────────│ goods_id     │         │ goods_id        │
│ name        │            │ name (颜色)   │         │ sku_code        │
│ price       │            │ values (JSON) │         │ price           │
│ main_pictures│           └──────────────┘         │ inventory       │
│ category_id │                                     │ specs (JSON)    │
└─────────────┘                                     └─────────────────┘
```

- **SPU**（Standard Product Unit）：标准产品单元，如「男童加绒格子衬衫」
- **SKU**（Stock Keeping Unit）：可售卖最小单元，如「蓝绿格 140/10T」—— 独立价格与库存
- **Spec**：规格维度元数据，如颜色、尺码的可选值列表

**specs JSON 示例**（`goods_skus.specs`）：

```json
[
  { "name": "颜色", "valueName": "黑白格【213379】" },
  { "name": "尺码", "valueName": "80/24M" }
]
```

#### 主键 / 外键设计思路

| 关系 | 设计 | 原因 |
|------|------|------|
| `goods_skus.goods_id` → `goods.id` | 逻辑外键（未建物理 FK） | 导入数据灵活；Sequelize `include` 关联查询 |
| `cart_items` | `(user_id, sku_id)` 业务唯一 | 同一用户同一 SKU 合并数量 |
| `order_skus.order_id` → `orders.id` | 一对多 | 订单明细独立表，支持多商品 |
| `orders.order_no` | UNIQUE 索引 | 业务单号全局唯一，防重复提交 |
| `orders.address_snapshot` | JSON 字段 | **快照模式**：下单时冻结地址，用户后续改地址不影响历史订单 |

#### 索引设计

| 索引 | 表 | 原因 |
|------|-----|------|
| `PRIMARY KEY (id)` | 全表 | 聚簇索引，主键查询最快 |
| `UNIQUE order_no` | `orders` | 支付回调、订单号检索 |
| `INDEX idx_mobile` | `sms_codes` | 按手机号查最近验证码，频率限制查询 |

#### 分表 / 优化说明

当前数据量为实训规模（商品约 100 SPU、800+ SKU），**未做水平分表**。已采用的优化：

- **JSON 字段**：`main_pictures`、`details_properties`、`address_snapshot` 避免多表 JOIN
- **订单快照**：`order_skus` 冗余 `name/image/attrs_text/cur_price`，避免订单展示 JOIN 商品表
- **分页查询**：`Order.findAndCountAll({ limit, offset })` 订单列表分页
- **后续可分表方向**：`orders` 按 `user_id` 哈希分表；`goods_skus` 按 `goods_id` 分区（超大规模时）

### 4.1 通用功能亮点

#### 亮点 A：一套代码三端运行（条件编译）

- **亮点描述**：同一 Vue 代码库产出 H5、微信小程序、App 三套产物。
- **实现原理**：构建期 `#ifdef` / `#ifndef` 剪枝，各端只打包对应平台代码。
- **专业技术概念**：**编译时代码隔离**、**平台 API 抽象**（`uni.*`）。
- **落地细节**：`src/config/index.ts` H5 开发用 `localhost:3000`，小程序用局域网 IP；`ChatPanel.vue` 三端图片转 Base64 各用 `FileReader` / `plus.io` / `getFileSystemManager`。
- **行业痛点**：多端重复开发人力成本高 → 复用率 90%+，维护一套业务逻辑。

#### 亮点 B：分包加载 + 预下载

- **亮点描述**：主包仅 TabBar 核心页，会员/订单放分包，控制小程序主包体积。
- **实现原理**：`subPackages` 按需加载；`preloadRule` 在「我的」页预载 `pagesMember`。
- **专业技术概念**：**小程序代码分包**、**按需注入**。
- **落地细节**：`pages.json` 中 `pagesMember`（4 页）、`pagesOrder`（4 页）；用户进「我的」后切地址管理近乎秒开。
- **行业痛点**：主包超 2MB 审核风险 → 首屏体积可控。

#### 亮点 C：SPU-SKU 规格联动选择

- **亮点描述**：多规格商品选「红色」后，无库存的「尺码」自动灰显。
- **实现原理**：预构建 `shopItemInfo` 字典（规格组合字符串 → SKU 对象）；`checkInpath()` 遍历候选组合判断是否存在于字典。
- **专业技术概念**：**路径检查算法**、**笛卡尔积规格组合**、**库存驱动 UI 状态**。
- **落地细节**：`vk-data-goods-sku-popup` 组件约 1400 行；`getArrayToSting(selectArr)` 作组合 key；选完所有维度后 `checkSelectShop()` 取价格库存。
- **行业痛点**：错选无货规格导致下单失败 → 前端拦截，提升转化。

#### 亮点 D：骨架屏 + 并行请求

- **亮点描述**：首页加载过程展示骨架屏，三个接口并行拉取。
- **实现原理**：`PageSkeleton` 在 `isLoading` 时渲染；`Promise.all([banner, category, hot])`。
- **专业技术概念**：**感知性能优化**、**Promise 并行化**。
- **落地细节**：`pages/index/index.vue` 的 `onLoad`；串行约 300ms → 并行取最慢接口约 100ms。
- **行业痛点**：白屏等待用户流失 → 骨架屏降低焦虑感。

#### 亮点 E：JWT 全链路鉴权 + 401 自动登出

- **亮点描述**：登录态跨页面持久化，token 过期自动跳转登录。
- **实现原理**：请求拦截器注入 `Authorization`；响应拦截 401 清 Store 并 `navigateTo` 登录页。
- **专业技术概念**：**无状态认证**、**请求拦截器模式**。
- **落地细节**：`src/utils/http.ts` + `useMemberStore` 持久化。
- **行业痛点**：多端登录态不一致 → 统一拦截器一处维护。

#### 亮点 F：短信验证码登录 + 三重防刷

- **亮点描述**：手机号 + 验证码登录，无需记密码；防恶意刷短信。
- **实现原理**：后端生成 6 位码存库；阿里云 `SendSmsVerifyCode`；校验后签发 JWT。
- **专业技术概念**：**OTP 一次性密码**、**频率限制（Rate Limiting）**。
- **落地细节**：10 秒内同号不可重发；验证码 5 分钟过期、`used=1` 一次性；前端 60 秒倒计时。
- **行业痛点**：密码泄露、弱密码 → 验证码 + 手机号实名链路更安全。

### 4.2 自研优化亮点

#### 亮点 G：自研 Express 全栈后端（替代纯 Mock）

- **亮点描述**：完整 Node.js 后端 + MySQL，非仅前端调第三方 Mock API。
- **实现原理**：RESTful 路由 + Sequelize ORM + 统一响应体 `{ code, msg, result }`。
- **专业技术概念**：**前后端分离**、**ORM 关联查询**、**领域模型拆分**。
- **落地细节**：`server/` 目录 15 个路由文件；`xiaotuxian.sql` 完整建表与种子数据；支持 `pnpm dev` + `tsx watch` 热重载。

#### 亮点 H：Pinia 跨平台持久化适配器

- **亮点描述**：登录态在 H5 / 小程序 / App 均能重启后恢复。
- **实现原理**：`pinia-plugin-persistedstate` 自定义 `storage` 接口，底层 `uni.setStorageSync`。
- **专业技术概念**：**适配器模式（Adapter Pattern）**、**存储抽象**。
- **落地细节**：`src/stores/modules/member.ts` 的 `persist.storage` 配置。
- **行业痛点**：插件默认 localStorage 导致小程序持久化失效 → 三端统一方案。

#### 亮点 I：Multer 内存直传 OSS（头像上传）

- **亮点描述**：用户头像上传不占服务器磁盘，直传对象存储。
- **实现原理**：`multer.memoryStorage()` → `ossClient.put(key, buffer)` → 更新 `users.avatar`。
- **专业技术概念**：**对象存储**、**零落盘上传**、**服务端签名直传**。
- **落地细节**：5MB 限制；仅 `jpg/png/gif/webp`；文件名 `avatars/avatar_{timestamp}_{random}.ext`。
- **行业痛点**：单机磁盘有限、图片拖垮服务器 → 存储与计算分离。

#### 亮点 I：图片代理 SSRF 白名单

- **亮点描述**：后端代理外链商品图，仅允许可信 OSS 域名。
- **实现原理**：`GET /proxy/image?url=` 解析 URL → 校验 `hostname` 在白名单 → `fetch` 转发。
- **专业技术概念**：**SSRF（服务端请求伪造）防护**、**域名白名单**。
- **落地细节**：`server/app.ts` 中 `ALLOWED_IMAGE_HOSTS` 数组；非法域名返回 403。
- **行业痛点**：开放代理被利用扫描内网 → 白名单最小权限。

#### 亮点 J：Docker 多阶段构建 + 非 root 运行

- **亮点描述**：生产镜像精简；后端容器不以 root 运行。
- **实现原理**：Builder 阶段编译 → Runtime 阶段仅拷贝产物；`adduser appuser` + `USER appuser`。
- **专业技术概念**：**多阶段构建（Multi-stage Build）**、**最小攻击面镜像**、**容器安全基线**。
- **落地细节**：前端镜像 ~50MB（Nginx）；后端 `HEALTHCHECK` 探活 `/health`；MySQL `healthcheck` + `depends_on: condition: service_healthy`。
- **行业痛点**：环境不一致、镜像臃肿 → 可复现部署。

#### 亮点 K：订单地址 JSON 快照

- **亮点描述**：下单瞬间将完整地址 JSON 写入 `orders.address_snapshot`。
- **实现原理**：提交订单时 `address?.toJSON()` 序列化存储，展示订单不再依赖实时地址表。
- **专业技术概念**：**数据快照（Snapshot）**、**最终一致性展示**。
- **落地细节**：`server/routes/order.ts` 的 `Order.create({ address_snapshot: ... })`。
- **行业痛点**：用户改地址后历史订单收货信息错乱 → 快照保证法务与客服可追溯。

- **亮点描述**：用户上传商品/场景图，AI 从美学、内容、搭配建议多角度分析。

- **专业技术概念**：**多模态大模型（VLM）**、**Base64 Data URL**。
- **落地细节**：三端条件编译读图；`IMAGE_ANALYSIS_PROMPT` 约束 200 字内 emoji 分段回复；支持 stream 版。

### 难点 3：小程序无法使用 Pinia 默认持久化

| 维度 | 内容 |
|------|------|
| **问题现象** | H5 刷新仍登录，小程序重启后 token 丢失 |
| **排查思路** | 查 `pinia-plugin-persistedstate` 文档，默认 `localStorage` 仅浏览器存在 |
| **最终方案** | Store 配置自定义 `storage.getItem/setItem`，内部调用 `uni.getStorageSync/setStorageSync` |
| **技术知识点** | 适配器模式、uni 本地存储 API |
| **优化效果** | 三端登录态一致持久化 |

### 难点 4：H5 生产环境跨域与 API 地址

| 维度 | 内容 |
|------|------|
| **问题现象** | 开发环境直连 `localhost:3000` 正常，生产 build 后跨域失败 |
| **排查思路** | 生产 `API_BASE` 为空字符串时请求变为相对路径；需 Nginx 将 `/home/` 等转发到 backend |
| **最终方案** | H5 生产 `API_BASE = ''`；`nginx/default.conf` 按路径 `proxy_pass` 到 `backend:3000`；开发环境仍直连 |
| **技术知识点** | 反向代理、同源策略、环境变量 |
| **优化效果** | 生产 H5 与 API 同域，无 CORS 问题 |

### 难点 5：AI 集成 — Tool 调度与流式转发

| 维度 | 内容 |
|------|------|
| **问题现象** | 直接调 LLM 会编造不存在的商品；OpenAI 适配器无法用于 MiMo；流式响应需手动解析 SSE  chunk |
| **排查思路** | 将「查商品」与「生成文案」解耦；继承 `BaseChatModel` 自定义 `_generate`；流式路径直接 `fetch` + `reader.read()` 解析 `data:` 行 |
| **最终方案** | 意图识别用关键词 + LangChain Tool 查库；非流式走 `MiMoChatModel`；流式走原生 fetch 转发 delta；异常时 Fallback 商品列表 |
| **技术知识点** | LangChain Tool、自定义 ChatModel、SSE 协议、Prompt 注入 |
| **优化效果** | 推荐商品 100% 来自数据库；H5 打字机效果流畅 |

### 6.3 功能三：AI 智能购物助手（全链路）

#### 前端交互

1. 首页悬浮 `AiAssistant`（Lottie 动画）→ 打开 `ChatPanel`
2. 用户输入或点快捷入口「穿搭推荐」
3. H5：`postAiChatStreamAPI` 收 `goods` 事件渲染商品卡片 + `chunk` 更新文字
4. 点击商品卡片 `navigateTo` 商品详情

#### 接口逻辑

```
POST /ai/chat/stream
  → findRelevantGoods(message)     // 关键词 → Tool 查库
  → sendEvent({ type: 'goods' })   // 先推商品
  → fetch MiMo stream:true         // 流式生成
  → sendEvent({ type: 'chunk' })   // 逐段推文字
  → sendEvent({ type: 'done' })
```

#### 后端业务 — 意图识别链

```typescript
// 优先级：分类关键词 → 全文搜索 → 随机推荐
async function findRelevantGoods(message: string) {
  for (const [keyword, categories] of Object.entries(KEYWORD_CATEGORY_MAP)) {
    if (message.includes(keyword)) {
      const result = await categoryGoodsTool.invoke({ category: cat })
      if (result !== '该分类下暂无商品') return JSON.parse(result)
    }
  }
  const searchResult = await searchGoodsTool.invoke({ keyword: message })
  if (searchResult !== '未找到相关商品') return JSON.parse(searchResult)
  return JSON.parse(await recommendTool.invoke({ limit: 5 }))
}
```

#### 数据存储

- 商品数据来自 `goods` + `goods_categories` 实时查询
- 会话记忆 `sessionMemories` 内存 Map（生产可换 Redis），保留最近 10 轮

#### 全链路

```
POST /sms/send
  → 校验手机号正则 /^1[3-9]\d{9}$/
  → 查 10s 内是否已发（防刷）
  → 生成 6 位码，expires_at = now + 5min
  → 阿里云 SendSmsVerifyCode

  → 查 sms_codes(mobile, code, used=0, expires_at > now)
  → used=1，User findOrCreate
  → jwt.sign → 返回 token
```

## 七、项目优化点 & 后续迭代规划

### 7.1 现有优化方案

| 优化项 | 实现 | 效果 |
|--------|------|------|
| 首页并行请求 | `Promise.all` | 减少首屏等待 |
| 骨架屏 | `PageSkeleton` 组件 | 降低感知延迟 |
| 分包预下载 | `preloadRule` | 会员页跳转加速 |

| 静态资源缓存 | `expires 30d` | 二次访问加速 |
| 图片代理缓存 | `Cache-Control: max-age=86400` | 减轻源站压力 |
| AI 意图本地识别 | 关键词表替代 LLM 分类 | 降低 API 成本与延迟 |
| 购物车 SKU 合并 | 同 SKU upsert 数量 | 避免重复行 |

### 7.2 性能优化细节（可继续深挖）

2. **接口**：订单列表 N+1 查询（循环查 `order_skus`）可改为单次 `IN` 查询或 Sequelize `separate: true` 优化
