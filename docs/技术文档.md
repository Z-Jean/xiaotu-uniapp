# 小兔鲜儿 — 鲜食电商平台技术文档

> 本文档用于 PPT 答辩，深入讲解项目核心亮点、技术难点、为什么用、怎么用、在哪里用。

## 一、项目概述

**小兔鲜儿** 是一个鲜食电商平台，基于 uni-app (Vue3 + TypeScript) 构建，通过条件编译兼容 **H5、微信小程序、App** 三端。

### 技术栈全景

| 层级 | 技术选型 | 说明 |
|------|---------|------|
| 前端框架 | uni-app + Vue3 + TypeScript | 跨平台开发 |
| 状态管理 | Pinia + 持久化插件 | 用户信息/购物车持久化 |
| UI 组件 | uni-ui (easycom) | 自动引入，无需手动 import |
| 后端框架 | Express.js + TypeScript | RESTful API |
| 数据库 | MySQL 8.0 | 商品、订单、用户数据 |
| 云存储 | 阿里云 OSS | 商品图片、用户头像 |
| AI 能力 | LangChain + MiMo LLM | 智能购物助手 |
| 地图服务 | 高德地图 API | 定位、地址选择、物流轨迹 |
| 短信服务 | 阿里云短信 | 验证码登录 |
| 容器化 | Docker + Docker Compose | 一键部署 |
| CI/CD | GitHub Actions | 自动部署到服务器 |

### 亮点 1：多端条件编译 — 一套代码，三端运行

#### 是什么？

uni-app 的条件编译是一种**编译时代码隔离**技术，通过 `#ifdef` / `#ifndef` / `#endif` 指令，让同一份代码在不同平台编译时只保留对应平台的代码。

#### 为什么用？

| 问题 | 条件编译的解决方案 |
|------|-------------------|
| H5 用 `localhost`，小程序不允许 | H5 编译 `localhost:3000`，小程序编译局域网 IP |
| 微信有 `wx.chooseMedia`，H5 没有 | 微信端编译 `chooseMedia`，H5 端编译 `chooseImage` |
| 小程序有 `open-type="contact"` 客服按钮 | 仅在微信端渲染该按钮 |
| App 端用 `plus.io.FileReader`，H5 用 `FileReader` | 各端编译各自的文件读取实现 |

**核心价值**：一套代码库同时产出 H5、小程序、App 三个版本，维护成本降低 60%+。

#### 怎么用？在哪里用？

项目中 **14 个文件、37 处** 使用了条件编译：

**场景 1：API 地址多端配置**

```typescript
// src/config/index.ts
// #ifdef H5
export const API_BASE = import.meta.env.DEV ? 'http://localhost:3000' : ''
// #endif

// #ifndef H5
export const API_BASE = 'http://10.107.246.104:3000'
// #endif
```

- H5 开发环境 → `localhost:3000`（浏览器直连后端）
- H5 生产环境 → 空字符串（走 Nginx 反向代理）
- 小程序/App → 局域网 IP 或域名

**场景 2：图片转 Base64 三端各自实现**

```typescript
// src/components/ChatPanel.vue

// H5 端：浏览器 FileReader
// #ifdef H5
const reader = new FileReader()
reader.onload = () => { pendingImage.value = reader.result }
reader.readAsDataURL(blob)
// #endif

// App 端：5+ API
// #ifdef APP-PLUS
const reader = new plus.io.FileReader()
reader.onloadend = (e) => { pendingImage.value = e.target.result }
reader.readAsDataURL(file)
// #endif

// 微信小程序端：FileSystemManager
// #ifdef MP-WEIXIN
const fs = uni.getFileSystemManager()
fs.readFile({ filePath, encoding: 'base64', success: (data) => {
  pendingImage.value = `data:image/jpeg;base64,${data.data}`
}})
// #endif
```

**场景 3：微信专属 UI 组件**

```html
<!-- 仅微信小程序渲染客服按钮 -->
<!-- #ifdef MP-WEIXIN -->
<button open-type="contact">客服</button>
<!-- #endif -->
```

#### PPT 讲解要点

> "条件编译是 uni-app 跨平台的核心能力。我们的项目在 14 个文件中使用了 37 处条件编译，覆盖 H5、微信小程序、App 三端。同一个功能（如图片上传），在三个平台使用完全不同的原生 API 实现，但代码共存于同一个文件中，编译时自动隔离。"

### 亮点 2：SKU 商品规格管理

#### 是什么？

SKU（Stock Keeping Unit，库存量单位）是电商系统的核心数据模型。一个商品（SPU）有多个规格维度（如颜色、容量），每个规格组合对应一个 SKU，拥有独立的价格和库存。

#### 为什么用？

| 电商需求 | SKU 模型的解决方式 |
|---------|-------------------|
| 一部手机有 6 种颜色 × 3 种容量 = 18 种卖法 | 18 个 SKU，每个有独立价格和库存 |
| 用户选择规格后显示对应价格 | SKU 联动算法实时计算 |
| 库存不足时禁用该规格组合 | 路径检查算法自动灰显不可选项 |
| 购物车以最小粒度管理 | 以 SKU ID 为唯一标识 |

#### 怎么用？

**数据库设计（三张核心表）**：

```
goods (SPU)          goods_skus (SKU)           goods_specs (规格定义)
┌──────────────┐     ┌──────────────────┐       ┌──────────────────┐
│ id           │◄────│ goods_id         │       │ goods_id         │
│ name         │     │ sku_code         │       │ name (颜色/容量)  │
│ price        │     │ price            │       │ values (JSON)    │
│ main_pictures│     │ inventory        │       └──────────────────┘
│ category_id  │     │ specs (JSON)     │
└──────────────┘     └──────────────────┘
```

**specs 字段示例**：
```json
[{"name": "颜色", "valueName": "红色"}, {"name": "容量", "valueName": "256G"}]
```

**SKU 选择核心算法**（`vk-data-goods-sku-popup` 组件）：

```
用户点击规格值 → checkInpath() 遍历所有组合
                → 检查当前已选 + 该值 是否存在于 shopItemInfo
                → 存在 = 可选（高亮）
                → 不存在 = 不可选（灰显）
                → 所有维度选完 → 取出对应 SKU → 显示价格/库存
```

#### 在哪里用？

- **商品详情页** (`src/pages/goods/goods.vue`)：SKU 选择弹窗
- **购物车** (`src/pages/cart/components/CartMain.vue`)：以 SKU ID 为粒度管理
- **订单创建** (`src/pagesOrder/create/create.vue`)：根据 SKU 计算总价

#### PPT 讲解要点

> "SKU 是电商系统的核心数据模型。我们设计了 SPU-SKU-Specs 三层数据结构，通过路径检查算法实现规格联动选择。用户点击红色时，自动灰显没有红色库存的容量选项。这个算法是前端组件的核心逻辑，约 200 行代码。"

### 亮点 3：AI 智能购物助手（LangChain）

#### 是什么？

基于 LangChain 框架 + 小米 MiMo LLM 构建的 AI 购物助手，支持自然语言对话、商品搜索推荐、图片分析。

#### 为什么用？

| 传统电商 | AI 购物助手 |
|---------|-----------|
| 用户手动搜索关键词 | 自然语言对话："推荐一款红色的手机" |
| 浏览分类找商品 | AI 理解意图后自动查询数据库 |
| 无法识别图片 | 上传图片 AI 分析并推荐相关商品 |

#### 怎么用？

**架构流程**：

```
用户消息 → 关键词意图识别 → LangChain Tool 调度（查询数据库）→ MiMo LLM 生成回复
```

**三步实现**：

**Step 1：自定义 LLM 适配器**

项目没有直接使用 `ChatOpenAI`，而是自定义了 `MiMoChatModel` 类继承 LangChain 的 `BaseChatModel`：

```typescript
// server/routes/ai.ts
class MiMoChatModel extends BaseChatModel {
  async _generate(messages) {
    const response = await fetch('https://api.xiaomimimo.com/v1/chat/completions', {
      method: 'POST',
      body: JSON.stringify({
        model: 'mimo-v2.5',
        messages: messages.map(m => ({ role: m.role, content: m.content })),
        max_tokens: 800,
        temperature: 0.7,
      })
    })
    // 解析返回...
  }
}
```

**Step 2：定义 LangChain Tools**

使用 `DynamicStructuredTool` + Zod Schema 定义 3 个工具：

| Tool | 功能 | 数据库查询 |
|------|------|-----------|
| `search_goods` | 关键词搜索商品 | `goods.name LIKE ?` |
| `category_goods` | 按分类查询 | 关联 `goods_categories` 表 |
| `recommend_goods` | 随机推荐热销 | `ORDER BY RAND()` |

**Step 3：确定性意图识别**

不依赖 LLM 做意图识别（成本高、延迟大），而是用关键词映射表：

```
"手机" → 分类查询
"红色" → 关键词搜索
其他 → 兜底推荐
```

#### 在哪里用？

- **AI 聊天面板** (`src/components/ChatPanel.vue`)：H5 端 SSE 流式响应
- **图片分析**：上传商品图片，AI 分析美学、内容、推荐相关商品
- **降级策略**：API 异常时自动返回商品推荐列表，不影响用户体验

#### PPT 讲解要点

> "我们集成了 LangChain 框架，但没有直接用 OpenAI，而是自定义了 MiMoChatModel 适配小米的 MiMo API。LangChain 在项目中主要扮演 Tool 编排框架的角色——定义搜索、分类、推荐三个工具，由 LLM 根据用户意图自动调用。这种架构既利用了 LangChain 的 Tool 调度能力，又避免了对 OpenAI 的依赖。"

### 亮点 4：阿里云 OSS 对象存储

#### 是什么？

阿里云 OSS（Object Storage Service）是海量、安全、低成本的云存储服务。项目用它存储用户头像和商品图片。

#### 为什么用？

| 本地存储 | 阿里云 OSS |
|---------|-----------|
| 服务器磁盘空间有限 | 海量扩展，按需付费 |
| 图片加载慢（单点） | CDN 加速，全国就近访问 |
| 服务器崩溃数据丢失 | 多副本冗余，99.999999999% 持久性 |
| 需要自己实现图片处理 | 内置缩放、裁剪、水印等处理 |

#### 怎么用？

**后端实现**（`server/routes/upload.ts`）：

```typescript
// 1. Multer 内存存储（文件不落盘）
const upload = multer({ storage: multer.memoryStorage(), limits: { fileSize: 5 * 1024 * 1024 } })

// 2. OSS 客户端配置
const ossClient = new OSS({
  region: process.env.OSS_REGION,
  accessKeyId: process.env.OSS_ACCESS_KEY_ID,
  accessKeySecret: process.env.OSS_ACCESS_KEY_SECRET,
  bucket: process.env.OSS_BUCKET,
})

// 3. 上传流程
router.post('/avatar', auth, upload.single('file'), async (req, res) => {
  const fileName = `avatars/avatar_${Date.now()}_${randomString}.${ext}`
  const result = await ossClient.put(fileName, req.file.buffer)  // 直传 OSS
  // 更新用户头像 URL
  await db.query('UPDATE users SET avatar = ? WHERE id = ?', [result.url, userId])
})
```

**关键设计**：
- **内存直传**：文件通过 Multer 存入内存，直接传 OSS，不落盘，减少服务器 IO
- **文件限制**：最大 5MB，仅允许 jpg/png/gif/webp
- **安全配置**：AccessKey 通过环境变量管理，不硬编码

#### 在哪里用？

- **用户头像上传**：个人中心修改头像
- **图片代理**：后端代理 OSS 图片，防止 SSRF 攻击（白名单机制）

#### PPT 讲解要点

> "我们使用阿里云 OSS 存储用户头像。关键设计是 Multer 内存存储 + ali-oss SDK 直传——文件在服务端不落盘，直接从内存传到 OSS，减少了服务器 IO 压力。AccessKey 通过环境变量管理，避免密钥泄露。"

### 亮点 5：Docker 容器化部署

#### 是什么？

使用 Docker 将前端（Nginx）、后端（Node.js）、数据库（MySQL）打包为三个容器，通过 Docker Compose 一键编排部署。

#### 为什么用？

| 传统部署 | Docker 部署 |
|---------|-----------|
| 手动安装 Node.js、MySQL、Nginx | 一条命令安装所有依赖 |
| 环境不一致导致 "在我电脑上能跑" | 容器镜像保证环境一致性 |
| 迁移服务器需要重新配置 | 镜像可直接迁移到任何服务器 |
| 无法快速回滚 | 镜像版本管理，秒级回滚 |

#### 怎么用？

**架构图**：

```
┌─────────────────────────────────────────┐
│  Docker Compose                          │
│                                          │
│  ┌─────────┐    ┌──────────┐            │
│  │  Nginx   │    │ Backend  │            │
│  │  :80     │───→│  :3000   │            │
│  │ 静态文件 │    │ Express  │            │
│  └─────────┘    └────┬─────┘            │
│                      │                   │
│                 ┌────▼─────┐            │
│                 │  MySQL   │            │
│                 │  :3306   │            │
│                 └──────────┘            │
└─────────────────────────────────────────┘
```

**多阶段构建（前端 Dockerfile）**：

```dockerfile
# Stage 1: 构建 H5 产物
FROM node:20-alpine AS builder
RUN pnpm install --frozen-lockfile
RUN pnpm build:h5

# Stage 2: Nginx 服务（仅含静态文件）
FROM nginx:alpine
COPY --from=builder /app/dist/build/h5 /usr/share/nginx/html
```

- 构建阶段：~200MB（Node.js + 依赖）
- 运行阶段：~50MB（Nginx + 静态文件）
- **最终镜像仅 50MB**，比单阶段构建减少 75%

**Nginx 反向代理**：

```nginx
# 前端静态文件
location / {
    try_files $uri $uri/ /index.html;  # SPA 路由
}

# 后端 API 代理
location /home/ {
    proxy_pass http://backend:3000/home/;  # 去掉 /api/ 前缀
}
```

**自动部署流程**：

```
git push main → GitHub Actions → SSH 连接服务器 → docker compose up -d --build
```

#### 在哪里用？

- **服务器部署**：`docker compose up -d` 一键启动三个容器
- **自动部署**：push 到 main 分支，GitHub Actions 自动构建并部署
- **数据持久化**：MySQL 数据通过 Docker Volume 持久化

#### PPT 讲解要点

> "我们采用 Docker Compose 编排三个容器：Nginx 服务前端静态文件并反向代理 API 请求，Express 运行业务逻辑，MySQL 存储数据。前端使用多阶段构建，最终镜像仅 50MB。通过 GitHub Actions 实现 push-to-deploy，开发者只需 git push，服务器自动更新。"

### 亮点 6：短信验证码登录

#### 是什么？

用户通过手机号 + 短信验证码登录，无需记忆密码，提升用户体验和安全性。

#### 为什么用？

| 密码登录 | 验证码登录 |
|---------|-----------|
| 用户需要记忆密码 | 手机验证码，无需记忆 |
| 密码泄露风险 | 验证码一次性使用 |
| 忘记密码需找回流程 | 直接获取新验证码 |
| 弱密码安全隐患 | 手机号实名认证 |

#### 怎么用？

**流程**：

```
用户输入手机号 → 点击获取验证码 → 后端调用阿里云 SMS API → 用户收到短信
→ 输入验证码 → 后端校验 → 登录成功 → 签发 JWT Token
```

**后端实现**：

```typescript
// 发送验证码
router.post('/send-code', async (req, res) => {
  const { mobile } = req.body
  const code = String(Math.floor(100000 + Math.random() * 900000))  // 6位随机数
  // 存储到数据库（5分钟有效）
  await db.query('INSERT INTO sms_codes (mobile, code, expires_at) VALUES (?, ?, ?)',
    [mobile, code, Date.now() + 5 * 60 * 1000])
  // 调用阿里云 SMS API
  await sendSMS(mobile, code)
})

// 验证码登录
router.post('/login/code', async (req, res) => {
  const { mobile, code } = req.body
  // 校验验证码
  const [rows] = await db.query(
    'SELECT * FROM sms_codes WHERE mobile = ? AND code = ? AND expires_at > NOW()',
    [mobile, code])
  if (!rows.length) return res.json({ code: '0', msg: '验证码错误或已过期' })
  // 签发 JWT Token...
})
```

**安全措施**：
- 10 秒频率限制（同手机号）
- 验证码 5 分钟过期
- 验证码一次性使用
- 阿里云平台级频率控制

#### PPT 讲解要点

> "我们集成了阿里云短信服务，实现验证码登录。后端生成6位随机验证码存入数据库（5分钟有效），调用阿里云 SMS API 发送短信。前端实现60秒倒计时防重复发送。这种方式既提升了用户体验，又避免了密码泄露风险。"

### 亮点 8：Pinia 状态持久化（跨平台适配）

#### 是什么？

使用 Pinia + pinia-plugin-persistedstate 实现状态持久化，关键创新是**自定义存储适配器**，使持久化在微信小程序端也能工作。

#### 为什么用？

| 默认持久化 | 自定义适配 |
|-----------|-----------|
| 仅支持 localStorage（H5） | 使用 uni.setStorageSync，三端通用 |
| 小程序端失效 | 小程序、App、H5 均可持久化 |

#### 怎么用？

```typescript
// src/stores/modules/member.ts
export const useMemberStore = defineStore('member', () => {
  // ...状态定义

}, {
  persist: {
    storage: {
      getItem(key) {
        return uni.getStorageSync(key)     // 三端通用 API
      },
      setItem(key, value) {
        uni.setStorageSync(key, value)
      },
    },
  },
})
```

**效果**：
- H5 端：数据存储在 localStorage
- 微信小程序端：数据存储在小程序本地存储
- App 端：数据存储在 native 存储
- 用户刷新页面或重启 App，登录状态不丢失

#### PPT 讲解要点

> "Pinia 默认的持久化插件只支持 localStorage，仅在 H5 端生效。我们通过自定义 storage 接口，使用 uni.setStorageSync 封装，使持久化在微信小程序和 App 端也能正常工作。这是跨平台开发中一个典型的适配器模式应用。"

### 亮点 10：性能优化策略

#### 1. 骨架屏（Skeleton）

```html
<PageSkeleton v-if="isLoading" />
<template v-else> ... </template>
```

数据加载期间展示骨架屏，减少用户感知的等待时间。

#### 2. 并行数据请求

```typescript
// 首页三个独立请求并行执行
await Promise.all([getHomeBannerData(), getHomeCategoryData(), getHomeHotData()])
```

串行需 300ms，并行只需 100ms（取最慢的一个）。

#### 3. 分包预下载

```json
"preloadRule": {
  "pages/my/my": {
    "network": "all",
    "packages": ["pagesMember"]
  }
}
```

用户进入"我的"页面时，预加载用户中心分包，后续跳转秒开。

#### 4. SSE 流式响应

AI 聊天使用 Server-Sent Events，逐 token 输出，用户无需等待完整响应：

```typescript
// src/services/ai.ts
const reader = response.body.getReader()
while (true) {
  const { done, value } = await reader.read()
  // 逐块处理 AI 回复
}
```

#### 5. 按需渲染

```typescript
// 订单列表：只有被点击过的 tab 才渲染
orderTabs.value.forEach((item, index) => {
  item.isRender = index === activeIndex.value
})
```

避免一次性渲染所有 tab 内容，减少 DOM 节点。

## 五、答辩常见问题

**Q1：为什么选择 uni-app 而不是原生开发？**
> A：uni-app 一套代码可编译到 H5、微信小程序、App 三端，维护成本低。条件编译技术可以处理平台差异，实现 90%+ 代码复用。

**Q2：SKU 选择的核心算法是什么？**
> A：路径检查算法。将所有 SKU 的规格组合存入字典，用户每次选择时遍历其他维度的可选值，检查组合是否存在。存在则可选，不存在则灰显。

**Q3：为什么用 LangChain 而不是直接调用 AI API？**
> A：LangChain 提供了 Tool 编排框架，可以定义多个工具（搜索、分类、推荐），由 LLM 根据用户意图自动调用。直接调用 API 需要自己实现 Tool 调度逻辑。

**Q4：Docker 多阶段构建的好处是什么？**
> A：构建阶段使用完整的 Node.js 环境编译代码，运行阶段仅包含 Nginx + 静态文件。最终镜像从 200MB 减小到 50MB，减少了攻击面和部署时间。

**Q5：如何保证 API 安全？**
> A：三层防护：1) JWT 认证 + 401 自动处理；2) 隐私协议强制校验；3) SSRF 白名单防护。Docker 部署还使用非 root 用户运行、环境变量管理密钥。

**Q6：短信验证码如何防止恶意刷取？**
> A：三重防护：1) 前端 60 秒倒计时；2) 后端 10 秒频率限制；3) 阿里云平台级频率控制。验证码 5 分钟过期、一次性使用。

**Q7：地图功能如何实现三端适配？**
> A：H5 端使用高德 JS API 绘制贝塞尔曲线轨迹，App 端使用静态地图图片，小程序端使用原生 map 组件。通过条件编译在各端渲染不同的地图实现。

**Q8：Pinia 持久化如何兼容小程序？**
> A：自定义 storage 接口，使用 uni.setStorageSync / uni.getStorageSync 封装，这两个 API 在 H5、小程序、App 三端都可用，实现了跨平台持久化。
